## How a check can answer

A check does not return pass or fail. It returns one of five outcomes,
because "I could not measure this" is a different statement from "this is
fine", and conflating the two is how an auditor reports a device secure
that was never actually examined.

| Outcome | Meaning | Counts as a finding |
|---|---|---|
| `SAFE` | Measured, and the value is the expected secure value | no |
| `CRITICAL` / `WARNING` | Measured, and the value is wrong | yes |
| `INFO` | Measured and reported, with no pass/fail opinion | no |
| `VERIFY` | Not measurable here, so deliberately unscored | no |
| `SKIPPED` | Not applicable to this transport, named as such | no |

A check routes itself to `VERIFY` by emitting one of four tokens, which
the engine recognises rather than each check inventing its own wording:

```
NOT_APPLICABLE
NOT_DETERMINED
NOT_OBSERVABLE
UNMEASURED
```

Why this exists: a probe denied by SELinux, or targeting a path that does
not exist, returns empty output. Scoring empty output as a pass means a
locked-down device audits cleaner than an open one. Every check that can
fail to measure must say so, and a test suite enforces it against a
simulated device where every probe is denied.

`INFO` covers the other direction. A check whose `safe_pattern` matches
everything (`.`, `.*`, `^.*$` and similar) is an inventory check, not a
test, and is reported as `INFO` rather than inflating the safe count.

## How the device is probed

A single check often uses several of these.

| Method | Checks |
|---|---:|
| Filesystem walks (find, ls, stat) | 212 |
| System properties (getprop) | 150 |
| Secure settings and device_config | 132 |
| Framework services (dumpsys, service) | 132 |
| procfs and sysfs | 131 |
| Package manager (pm, cmd) | 91 |
| Process table (ps) | 28 |
| Kernel and app logs (dmesg, logcat) | 13 |
| Raw block device reads (dd) | 5 |

All device-side probes are POSIX shell, written for bionic and toybox
rather than GNU. That rules out a set of things which work on a Linux
workstation and fail silently on a phone:

- bionic `regcomp` is POSIX-only, so GNU extensions (`\|`, `\b`, `\s`,
  `\w`, `\d`) are treated as literals rather than rejected
- toybox `find` rejects `-executable`, `-readable`, `-printf`, `-newermt`
- `grep -c` prints `0` and exits non-zero, so `|| echo 0` prints `0` twice
- `od` collapses repeated identical lines to `*` unless `-v` is passed
- SELinux denies `stat` as well as `read`, so `[ -e ]`, `[ -r ]` and
  `[ -x ]` report a denied path as absent

A hygiene suite rejects each of these at the bundle level, so a new check
cannot reintroduce them.

## Host-side analysis

One subsystem does not run on the device. No Android shell can parse
ASN.1: AOSP ships no `openssl` and toybox has no ASN.1 support. So
certificate bytes are read off the device, parsed on the host, then folded
back into the normal check stream as ordinary rows.

| ID | Finding | Threshold |
|---|---|---|
| `CERT-WEAKKEY-001` | Trusted CA with a weak key | RSA/DSA under 2048 bits, EC under 256 |
| `CERT-WEAKSIG-001` | Trusted CA with a weak signature algorithm | md2, md4, md5, sha1 |
| `CERT-EXPIRED-001` | Expired trusted CA | past `notAfter` |

These were previously rendered in a separate table, which meant an expired
or weak trust anchor never reached the findings count, the risk score or
the attack chains.

User-installed CA certificates are deliberately excluded here. Three
device-side checks already score them as critical, and scoring them in
both places would make one condition produce two findings.

## Known gaps

Listed because an audit tool that hides its blind spots is worse than one
with fewer checks.

| Gap | State |
|---|---|
| Certificates expiring soon | `EXPIRING_SOON` and `CHECK` certificates appear in the HTML certificate table but produce no check row, so they do not reach the findings count or the risk score. Only already-expired certificates are scored. |
| Rollback index values | Reported as `info` only, so a device shipping with rollback protection effectively disabled is printed rather than flagged. |
| Root of trust fingerprint | Nothing compares `ro.boot.vbmeta.digest` against an expected baseline, so a device anchored to a strong but attacker-controlled key passes every boot check. |
| Key storage backend | `BOOT-ROTKEY-001` reports where the verified boot anchor lives. The equivalent for app and system keys is not built: TEE identity is readable from properties, but the four existing keystore checks all call `pm list features` or `lshal`, so they are binder-gated and report nothing over SSH or UART. |
| OTP and eFuse contents | Not attempted. Paths are per-SoC and usually root-only, so any probe would be guesswork presented as a measurement. |
| Treble / VINTF | No coverage. Judged a vendor-interface correctness property rather than a security control. |
| Memory corruption exploitability | Out of scope by policy. Checks report configuration and exposure, never exploitation. |

## Adding a check

A check is a JSON object. No Python is involved.

```json
{
  "id": "STOR-FBECIPHER-001",
  "category": "STORAGE",
  "label": "Userdata Contents Encryption Cipher",
  "command": "...POSIX shell...",
  "safe_pattern": "^fbe_contents=(OK|ADIANTUM)\\b",
  "level": "warning",
  "empty_is_safe": false,
  "description": "why this matters and what the verdict rests on",
  "remediation": "the minimal correct fix"
}
```

### Enforced by tests, not by review

These run against the whole bundle on every commit.

| Rule | Test |
|---|---|
| A probe that cannot measure must emit an unmeasured token, not empty output | `test_cannot_determine_tokens_have_an_unmeasured_branch` |
| No check may report a finding on a device where every probe is denied | `test_denied_device.py` |
| Every command must parse under POSIX `sh`, including nested `sh -c` | `test_every_command_parses_under_posix_sh`, `test_inner_sh_c_scripts_also_parse` |
| No GNU regex extensions in `grep` patterns | `test_grep_patterns_use_no_gnu_regex_extensions` |
| No GNU-only `find` predicates | `test_find_uses_no_gnu_only_predicates` |
| `grep -c` must not double its count | `test_grep_c_does_not_double_its_count` |
| `$( (` must not be written as `$((` | `test_no_subshell_opened_as_arithmetic_expansion` |
| A tree search must not hide an incomplete walk | `test_tree_searches_do_not_hide_an_incomplete_walk` |
| Binder output must not be counted without a guard | `test_binder_output_is_not_counted_without_a_guard` |
| Counting checks must not treat empty as safe, and must still be able to pass | `test_counting_checks_do_not_treat_empty_as_safe`, `test_count_emitting_checks_can_still_pass` |
| Every check must be capable of failing | `test_failable_checks_are_capable_of_failing` |
| IDs and labels unique across the bundle, and labels not confusable | `test_ids_are_unique_across_all_files`, `test_labels_are_unique_across_all_files`, `test_labels_are_not_confusable` |
| No two checks may share a command, or scan the same name set | `test_no_two_checks_share_a_command`, `test_no_two_checks_scan_the_same_name_set` |
| No count-and-list pair of the same probe | `test_no_count_and_list_pairs_of_the_same_probe` |
| Every check must carry remediation text | `test_every_check_has_remediation_text` |
| No em dashes anywhere in check text | `test_no_em_dashes_in_check_text` |
| Every `safe_pattern` must compile | `test_all_safe_patterns_compile` |
| Counts quoted in `README.md` must match the bundle | `test_readme_badge_counts_match_reality`, `test_readme_prose_check_counts_match_reality`, `test_readme_category_table_counts_match_reality` |

### Design rules, enforced per case

One misconfiguration must not produce two findings. Two checks may read
the same property only when they ask different questions of it: the three
security-patch-level CVE checks share `ro.build.version.security_patch`
but apply different cutoff dates, which is three tests from one input
rather than one test three times.

Where two checks score adjacent values, each verdict must be a function of
one property alone. The cipher checks are the worked example: one scores
the contents mode, the other the filenames mode, and
`test_each_cipher_check_depends_on_exactly_one_property` asserts each
verdict is constant across every value of the property it does not own.
That test exists because the first version of the contents check also
scored the filenames mode, so an Adiantum device produced two findings for
one setting.

An inventory check sidesteps the question by scoring nothing. It reports
facts at `INFO` and leaves the verdict to whichever check owns it.

## What a finding must carry

Every row in a report carries its own evidence, so a verdict can be
checked rather than trusted:

- the exact command that ran
- raw stdout and stderr, kept separate
- the exit code
- the basis for the verdict, in words

stderr cannot satisfy a `safe_pattern`. A denial message that happens to
contain an expected string does not make a check pass.
